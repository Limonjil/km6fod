## F21 — режим «держать дисплей интерактивным» (hold mode)

Реализован (`src/hold_mode.cpp`): wakelock `km6fod_dark` + подсветка 0 + повторное
зажигание через движок раз в 15 с. **Отключён**: вход был привязан к переходу
`DisplayState → LOCKSCREEN`, а это событие приходит и когда экран **будится** на
локскрин — режим гасил панель прямо перед глазами (измерено: `hold: entered` сразу
за `input keyevent 224`, затем чёрный экран).

Что нужно для корректного включения: настоящий триггер «экран погас» (сейчас его
нет ни в `DisplayState`, ни в AIDL), либо порог по подсветке с гистерезисом.
Код оставлен, вызов закомментирован в `session.cpp`, восстановление яркости
работает (`holdModeRecover` при старте HAL, в `uninstall.sh`, таймаут 30 мин).

## F23 — режим удержания удалён

`hold_mode` писал яркость в узел подсветки в обход фреймворка и разъезжался с ним:
после разблокировки подсветка оставалась гореть, а на локскрине могла не зажечься.
Симптом воспроизведён и вылечен: яркость снова применяет фреймворк
(`settings put system screen_brightness` → узел меняется: 45 → 723, 120 → 1927).
Режим удалён целиком (`src/hold_mode.*`, вызовы, блок в `uninstall.sh`), вместе с
uinput-инжектором, держателем жеста и `wake_helper.sh`. Осталось: один процесс
`fp_hal`, один Magisk-модуль.

## F24 — попытка №2 режима удержания: механизм есть, автомат нестабилен

Правильная схема (яркость через фреймворк, а не через узел) подтверждена:
`settings put system screen_brightness 0` из фонового контекста Magisk работает
(rc=0, узел становится 0). Помощник `hold.sh` берёт wakelock, растягивает
`screen_off_timeout`, гасит подсветку и возвращает всё назад.

Проблема: автомат входа/выхода осциллирует — вход по условию «bl==0 и настройка>0»
и выход по файлу `hold_off` (создаётся HAL на любое касание вне зоны сенсора)
срабатывают в одном цикле, режим входит и сразу выходит. Нужен явный конечный
автомат с приоритетами и журналом каждого решения, а не два независимых условия.

Старт помощника из `service.sh` **отключён**, файл оставлен.

**Гипотеза (доказана).** Окно тишины отсчитывалось от `startEnumerate()`, то есть от

(400 мс) закрылось пустым **до** того, как движок вообще начал перечислять. Уведомление,
пришедшее следом, было отброшено как «outside enumeration». Пустой список ушёл как
авторитетный (H-10: «пустой список — это ответ»), и фреймворк стёр регистрацию.

Признак того, что дело именно в окне, а не в движке: второй enumerate, начатый через
33 мс после уведомления, получил тот же id и отдал 1 шаблон.

**Правка.**

- `src/session.cpp:1900` — после `engine.enumerate()` окно перевзводится: `enum_started_ms_`
  и `enum_last_notice_ms_` = `monotonicMs()`. Бюджет `kEnumerateMaxMs` тоже считается от
  вызова движка, а не от вызова фреймворка.
- `src/session.cpp:1048` — уведомление движка записывается **всегда**, даже вне окна:
  движок вправе сообщить id во время `open()`/`set_active_group()`, и это правда о
  хранилище, а не мусор. `startEnumerate()` чистит буфер, поэтому вперёд ничего не течёт.
  Строка `enumerate notice ... outside enumeration` осталась как след.

**Проверка.** `build.sh` чисто, `patch_site.sh` PASS, `aidl_version.sh` PASS, zip
`a5660eca…`, `build/fp_hal` = `ec244d0d`.

**Прогноз на следующий бой (тест T0).** Первый же enumerate отвечает `1 template(s)`,
`enrolledList size:` остаётся 1, `settings_fingerprint_0.xml` не пустеет. Если БД уже
пуста (её стёрли в этом бою), фреймворк сначала попросит удалить «неизвестный» шаблон —
это ожидаемо, после этого регистрация делается заново.

**Урок.** Таймер окна надо вешать на действие движка, а не на запрос фреймворка; иначе
медленный `open()` съедает всё окно. Это же правило относится к `finishChallenge`:
settle калибровки отсчитывается от `preEnroll()` (см. правку выше).

## 09.11 — фантомные отпечатки: id шаблона схлопывался в 0 (`frameworkEnrollmentId`)

**Наблюдение (устройство, 10:31).** Владелец: два пальца (большой и указательный) стоят
на нуле при записи, остальные пишутся. `dumpsys fingerprint` → `count:0`, мастер записи
для этих пальцев не даёт ни шага прогресса (`session: enroll issued rc=0`, у вендора
`silfp_enroll_command: enroll-------------` и тишина), для остальных шагов идут до 20/20.
В `/data/vendor_de/0/fpdata` только `fpcal*.dat` — шаблоны лежат в TA, не в FS.

**Гипотеза.** `frameworkEnrollmentId()` (`src/session.cpp`, было `engine_id >= 0 ?

engine_id : 0`) превращает любой отрицательный id движка в `0`, а
`handleEnumerateMessage` отрицательные id в список не кладёт вовсе — только считает
(`enum_negative_count_`). Движок отдаёт шаблоны с отрицательными id (`-4293707`,
`-6827783`), значит: (1) два разных шаблона называются одним `0`; (2) фреймворк при
удалении посылает `remove(0)`, а в TA такого id нет → шаблон не удаляется; (3) при
повторной записи того же пальца движок видит существующий шаблон и не начинает запись.

**Тест, отличающий гипотезу.** Отдать id в исходном виде (без потери знака) и посмотреть,
перечислит ли фреймворк оба шаблона и вызовет ли `remove` с настоящими id. Если гипотеза
верна — `session: remove(<большое положительное>) rc=0` и пальцы записываются.

**Правка.** `src/session.cpp`: `frameworkEnrollmentId()` снимает знаковый бит
(`id & 0x7fffffff`), добавлен обратный `engineEnrollmentId()`, который ставит его обратно
