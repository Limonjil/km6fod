# Ревью цепочки подсветки (HBM) для FOD

Документ описывает, как цепочка устроена **сейчас**, что в ней сломано (с
доказательствами из кода и логов) и как она должна выглядеть. Правок в код не
внесено.

---

## 1. Как цепочка устроена сейчас

```
framework: authenticate/startAuth
        │
        ▼
armCapture(open_window = false)          session.cpp:600-618
        │  illumination_pending_ = true
        │  (свет НЕ включается — «deferred until touch»)
        ▼
touch reader thread ──► Session::onTouchEvent(x, y, down)      session.cpp:1146
        │
        ├─ state == kIdle  ИЛИ  (inside && !uiReadyValid())
        │      └─ wakeDisplay(); return;        ← свет не включается
        │
        └─ capturing && inside && !ignore_touches
               ├─ fresh_down = !finger_down_.exchange(true)    session.cpp:1231
               ├─ illumination_pending_ ? armIlluminationNow(true)
               │                        : if (!isOn) armIlluminationNow(false)
               └─ syncFingerStatusOptic(true)

armIlluminationNow(allow_wake)                                 session.cpp:520
        ├─ если display_asleep && allow_wake:
        │      wakeDisplay(); ждать до 2×150 мс «display_state ушёл из AOD»
        │
        ├─ если HbmController::isOn():
        │      requestOff(); sleep 30 мс;              ← «сброс окна»
        │
        └─ 8 × [ requestOn() ; sleep 80 мс ]           ← до ~7 секунд блокировки

HbmController::requestOn()                                     hbm.cpp:363
        ├─ если уже on → re-send uevent, return true
        └─ иначе worker: write("1") → readback 0xOK (до 3 попыток)
                          → sleep 90 мс → uevent FULL_HBM_SET
           вызывающий ждёт до 800 мс (kRequestTimeoutMs)

HbmController::requestOff()                                    hbm.cpp:416
        └─ want_on_=false; ++epoch_; deadline = now + 400 мс
           → worker или guard гасят панель и шлют FULL_HBM_CLEAR
```

Выключение света инициируется **из четырёх независимых мест**:
`release_token_`-задача (дебаунс отпускания), `finishOperation(close_hbm=true)`,
пути `cancel`/`timeout`, и сторожевые таймеры `HbmController`.

## 3. Дефекты

### D1 (критично). Взвод только на «свежее» касание

`fresh_down` (session.cpp:1231) вычисляется один раз и далее `finger_down_`
держится истинным до отложенного отпускания. Если окно погасло по любой
причине (D3, D4), все последующие кадры пальца **не могут** его зажечь — они
проходят мимо ветки взвода.

Следствие: «загорается не всегда», «надо приложить несколько раз».

### D2 (критично). Блокировка потока тача до нескольких секунд

`armIlluminationNow` вызывается **синхронно из потока чтения тача**
(fingerprint_hal.cpp:161) и внутри крутит до 8 попыток `requestOn()`. Каждая
неудачная попытка — это таймаут 800 мс (hbm.h:61) плюс пауза 80 мс
(session.h:153). Худший случай — около 7 секунд.

Пока поток заблокирован:
* кадры пальца не читаются → движок не получает `sendTouchInfo`;
* отпускание не обрабатывается → окно и статус пальца висят;
* пользователь видит «залипание» и «медленно».

### D3 (критично). «Сброс» окна выключает уже горящий свет

session.cpp:563-567: если программный флаг `isOn()` истинен, вызывается
`requestOff()`, затем пауза 30 мс и новая попытка включения. Любой повторный
взвод во время съёма даёт видимый провал: off → 90 мс → on. Именно это
наблюдается как мигание.

При этом «сброс» не проверяет факт: панель могла уже потерять HBM после
suspend, а флаг остался истинным.

### D4 (критично). Четыре независимых владельца выключения

`requestOff()` инкрементирует `epoch_`, что **отменяет** идущий `applyOn`.
Последовательность «включить → кто-то из четырёх погасил → включить не успели»
воспроизводится регулярно, потому что:
* дебаунс отпускания (600 мс) и `finishOperation` живут независимо;
* ожидание в `requestOn` (800 мс) дольше, чем 600 мс дебаунса.

Итог: свет включается и гаснет сам, без касаний (см. 41:39.108).

### D5 (важно). Решения опираются на ненадёжный `display_state_`

Он обновляется только в `onContextChanged`/`*WithContext` и часто устарел.
Из него выведены: «тёмный экран, будить», «дисплей спит, ждать», «результат
можно отдавать». Отсюда 300 мс простоя (2-й факт) и целый класс
недетерминированности.

### D6 (важно). Нет единого признака «палец на стекле»

Три источника: `finger_down_` (сессия), `gesture_token_` (жест), кадры тача.
Плюс два разных дебаунса (`kOpticReleaseMs`, `kWindowHoldMs`) и ещё
`kGestureHoldMs` для жеста. Они не согласованы между собой.

### D7 (средне). Признак готовности UI приходит из двух мест

`notifyUiReady(1)` вызывается и в `armCapture` (session.cpp:654), и в
`armIlluminationNow` (session.cpp:571), и ещё в двух местах (771, 1771).
Движок не может отличить «панель реально яркая» от «мы просто так сказали».

### D8 (средне). Лишние пробуждения

При каждом касании на тёмном экране отправляется `KEY_WAKEUP`, даже если
экран уже подняли 10 мс назад (36.872, 37.884, 38.035). Это дебаунс 120 мс
против трёх источников (ветка «без оверлея», взвод, путь разблокировки).

## 4. Как должно быть

Одна машина состояний, один владелец выключения, никакой блокировки читателя.

```
IDLE ──(down внутри зоны и оверлей готов)──► ARMING ──(панель подтверждена)──► ON
  ▲                                             │                              │
  └──────────(операция завершена)───────────────┘                              │
                                                                               │
ON ──(нет ни одного down-кадра > 600 мс)──► OFF_PENDING ──(down)──► ON         │
                                        └──(операция завершена)──► IDLE ◄──────┘
```

Правила, которые надо соблюсти:

1. **Взвод на каждом down-кадре**, пока панель не подтверждена. `requestOn()`
   уже идемпотентен для открытого окна — повторный вызов почти бесплатен.
   Ветку `fresh_down` для подсветки убрать.
2. **Никаких выключений в ответ на отпускание.** Отпускание только продлевает
   дедлайн. Гасим по дедлайну, по завершению операции или сторожем.
3. **Никакого «сброса» через off/on.** Вместо этого — перечитать узел и, если
   он не `0xOK`, повторить запись. Off/on оставить только для случая, когда
   панель действительно потеряла состояние (после suspend).
4. **Не блокировать поток тача.** Взвод выполнять асинхронно (в dispatcher),
   а кадры читать дальше: движку нужен `sendTouchInfo` непрерывно.
5. **Единственный признак «экран поднят» — валидный оверлей** (`uiReadyValid`),
   а не `display_state`. `display_state` использовать только для диагностики.
6. **Один признак пальца** — `finger_down_` с одним дебаунсом, общим для жеста
   и кадров.
7. **Один владелец выключения** — сама машина состояний; `finishOperation`
   и `cancel` только выставляют ей «операция завершена».
8. **`notifyUiReady(1)` — ровно в одном месте**, после подтверждённой панели.

Ожидаемый результат: свет включается на первом же кадре пальца (после того как
оверлей готов), гаснет через ~600 мс после реального ухода пальца, не мигает и
не зависит от того, сколько раз пользователь приложил палец.

## 5. Что менять (по порядку и по одной причине за раз)

1. Убрать `fresh_down` из пути подсветки; взводить на каждом down-кадре,
   пока окно не подтверждено. (D1)
2. Убрать блокирующий цикл из потока тача: `armIlluminationNow` → постановка
   задачи в dispatcher, сам `onTouchEvent` только фиксирует кадр. (D2)
3. Убрать «сброс через off/on»; заменить проверкой узла. (D3)
4. Свести выключение к одному дедлайну в сессии; `finishOperation`/`cancel`
   только выставляют флаг завершения. (D4)
5. Заменить решения по `display_state` на `uiReadyValid`. (D5, частично уже
   сделано в рабочем дереве, не проверено на устройстве)
6. Свести дебаунсы к двум константам и одному признаку пальца. (D6)
7. Оставить `notifyUiReady` в одном месте. (D7)
8. Дебаунс пробуждения — один, общий для всех путей. (D8)

Пункты 1-4 меняют поведение, 5-8 — гигиена. Проверять после каждого пункта,
а не все сразу.

## 6. Что в цепочке сделано правильно и трогать не надо

* Проверка записи чтением `0xOK` (hbm.cpp:229-260) — единственный способ
  отличить реальное включение от «драйвер молча проглотил команду».
* Инъекция `TRAN_FULL_HBM_EVENT` вместо патча ядра (uevent.cpp).
* Отдельный worker-поток для sysfs, чтобы binder-потоки не спали.
* Сторожевые таймеры (`kInactivityMs`, `kAbsoluteMaxMs`, `kApplyHardLimitMs`) —
  защита от «залипшего» света, их сохранить.
* `writeOffIndependent` с новым fd — переживает заклинивший worker.
