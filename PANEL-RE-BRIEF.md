# Бриф: реверс панели/тача для «настоящей тьмы» + разблокировки пальцем

Документ самодостаточный: всё, что нужно для начала работы, включая уже снятые факты.
Составлен по итогам сессии 04–05.11 на реальном устройстве.

## 2. Что требуется получить в итоге (критерии приёмки)

Пользовательский сценарий (сейчас НЕ работает без костыля):

1. Нажал питание → экран **полностью тёмный**: подсветка 0, никакого AOD-свечения.
2. Приложил палец к зоне сенсора → подсветка сенсора вспыхнула, телефон **разблокировался**, без второго касания/нажатия.
3. Нажал питание на тёмном экране → **с первого раза** виден локскрин, и он не гаснет.
4. Расход в простое сопоставим с обычным сном (см. §6: сейчас костыль стоит ~350 мА).

Приёмка — только измерениями, не «на глаз»:

- **Расход**: A/B по 5 минут через `/sys/class/power_supply/battery/current_now` — (a) обычный сон, (b) целевое состояние. Цель: разница в пределах ~10–15 %.
- **Задержка**: из `logcat` (тег `km6fod`) время от события касания до `authentication succeeded` — цель **≤ 400 мс** (сейчас ~200 мс от света до успеха, но только при включённом дисплее).
- **Тьма**: `cat /sys/class/leds/lcd-backlight/brightness` = `0` **и** `/sys/kernel/tran_display/lcm_hbm_state` = `0xFA`, плюс отсутствие свечения при фото с выдержкой.
- **Отсутствие регрессий**: записи отпечатка не теряются (`dumpsys fingerprint` — `count` не меняется), HAL не падает, локскрин достижим одним нажатием.

Допустимые варианты решения (в порядке предпочтения):

- **A.** Штатная последовательность через sysfs/procfs/DRM — без патчей вообще.
- **B.** Бинарный патч **своего** `adaptive-ts.ko` (или связанного модуля) с точными смещениями, применённый при загрузке к копии устройства (не поставка пропатченного блоба), с проверкой байтов и откатом.
- **C.** Доказанное «на этой панели нельзя» + лучший достижимый компромисс с числами (тогда решение принимает владелец).

## 3. Предыдущий костыль — УДАЛЁН (важно для контекста)

Раньше модуль держал дисплей интерактивным и обнулял подсветку через узел: shell-помощник
брал display-wakelock (`app_process`, FULL_WAKE_LOCK) и писал `0` в
`/sys/class/leds/lcd-backlight/brightness`; HAL по касанию инжектил `KEYCODE_WAKEUP`,
иначе SystemUI не создавал операцию `authenticate`.

Почему удалён:

1. **Цена**: ~350 мА в целевом состоянии (замер: 10 выборок по 2 с; ёмкость 5160 мА·ч →
   ~14–15 ч от полного заряда).
2. **Два писателя в один узел**: наш же `KEYCODE_WAKEUP` заставлял фреймворк переписать
   яркость, помощник принимал это за действие пользователя и выходил/входил снова каждые
   10–15 с.
3. Панель формально оставалась включённой — тратились SoC и дисплейный тракт.

Что осталось в коде после удаления (полезно знать):

- `hold.sh`, `files/hold.dex`, `tools/hold/` удалены; `service.sh` больше не запускает
  помощник и чистит его runtime-файлы.
- HAL больше не пишет `hold_off` (сигнал «отдай экран»); `src/paths.h` без `kHoldOffPath`.
- Инъекция `KEYCODE_WAKEUP` в HAL **осталась** — это единственный способ заставить SystemUI
  отрисовать ключгард и создать операцию `authenticate` при тёмном экране.

Следствие: сейчас на тёмном (по-настоящему спящем) экране **тач не отдаёт события** —
контроллер в `TRAN_GESTURE_SUSPEND_MODE`. Именно это и надо решить реверсом.

## 4. Твёрдо установленные факты (не переоткрывать)

Все пункты проверены на устройстве, часть — с отрицательными контролями.

### Подсветка
- `echo 0 > /sys/class/leds/lcd-backlight/brightness` при **включённом** экране обратимо:
  `723 → 0 → 300 → 723` (проверено чтением узла после каждой записи).
- При **выключенном/спящем** дисплее записи в узел игнорируются (драйвер пишет в лог
  `display state is slept or idle, skip set hbm node`). Именно поэтому «погасить, потом вернуть»
  не работает: порядок операций критичен.
- `cmd display set-brightness 0` зажимается фреймворком до минимума: `bl=16` (видимое свечение).
- Диапазон: `min_brightness=1`, `max_brightness=5119`; `settings 45` → узел `723`.
- В каталоге есть `led_mode` (`4` в норме), запись в него **запрещена** (`Permission denied`,
  только чтение) — но именно он подозревается в «залипании» нуля.

### Тач
- Режимы в `dmesg` (`tran_touch-INFO state_change_machine`):
  `TRAN_ACTIVE_MODE` ⇄ `TRAN_GESTURE_SUSPEND_MODE`; переход в suspend — примерно через 1 с после
  гашения, обратный — при пробуждении.
- В `GESTURE_SUSPEND` MT-события не отдаются вообще, но **жест приходит**: при касании зоны сенсора
  драйвер логирует `fts_gesture_readdata: gesture_id=36, point_num=1` →
  `GestureIdTranslate: g_gtp_gesture=0xcc` → `GestureHandle: Sorry, this gesture has been disabled`.
  То есть железо и прошивка контроллера палец видят, а драйвер выбрасывает событие.
- Разрешение жестов: `/proc/gesture_function`, формат — **2 символа имени + `1`/`2`** (вкл/выкл):
  `echo cc1` → `gesture_data_write code1[cc] enable[1]`, `echo fp1` → `code1[be] enable[1]`.
  Таблица имён найдена в строках `adaptive-ts.ko`:
  `al, cc, aa, bb, ab, ba, 5e, 3e, fp, w0/w, o0/o, m0/m, e0/e, c0/c, z0/z, s0/s, v0/v`.
  Включение `cc1` **не** привело к событию в userspace — что делает драйвер после прохождения
  проверки, не установлено (это задача реверса).
- Старый вендорский путь `ITrantp` `(2,3,"fp1")` пишет **не в тот узел** (`/proc/nvt_selftest`),
  ядро отвечает `Invalid value! count = 3`. Рабочий путь — только `/proc/gesture_function`.

### Дисплей/панель
- `/sys/kernel/tran_display/`: `lcm_name`, `lcm_hbm_state` (`0xOK` — HBM вкл, `0xFA` — выкл),
  `lcm_doze_backlight` (статично `lcm_doze_backlight:3;2;11;22;`), `lcm_dimming_state`
  (`dimming status:1`), `lcm_pcd_check`, `lcm_pcd_check_by_read_lcm`.
- HBM включается инъекцией uevent `TRAN_FULL_HBM_EVENT=FULL_HBM_SET` (наш HAL это делает в netlink
  multicast-группу 1) и/или записью в `lcm_hbm_state`. Драйвер **игнорирует HBM**, когда дисплей
  не интерактивен.
- AOD/doze на этой GSI фактически не работает: `DozeService` стартует (`canDoze=true`), но дисплей
  остаётся `mState=OFF`, AOD не рисуется.

### Фреймворк
- `OperationContext.displayState`: `LOCKSCREEN=1`, `NO_UI=2`, `AOD=4`, `UNKNOWN=0`. Это **состояние UI,
  а не питание**: после разблокировки приходит `NO_UI`, при локскрине — `LOCKSCREEN`.
- Операция `authenticate` создаётся только когда SystemUI считает экран интерактивным и отрисовал
  FOD-оверлей. Инъекция `KEYCODE_WAKEUP` — минимальный способ этого добиться; wakelock сам по себе
  не помогает (`overlay did not appear`, `state=0`).
- Тайминги реального успеха (logcat `km6fod`): `hbm: on` → `overlay appeared` +50 мс →
  `onAcquired(1) code 0` +147 мс → `authentication succeeded` → `unlocked`. Итого ~200 мс.
  Фреймворк создаёт операцию примерно через 1.3 с после пробуждения — это надо учитывать в бюджете.

## 7. Вопросы, на которые нужен ответ из реверса

1. **`led_mode`** (`/sys/class/leds/lcd-backlight/led_mode`, значение `4`): кто его выставляет, что он
   значит, есть ли штатный путь выставить яркость 0 и вернуться без ребута. Запись из userspace
   запрещена — вероятно, атрибут только для чтения; проверить по `.ko`/DT, кто пишет.
2. **AOD-яркость**: `lcm_doze_backlight` — это AOD-уровень? Можно ли держать панель в doze с
   нулевой подсветкой, сохранив `TRAN_ACTIVE_MODE` (или дав контроллеру остаться в режиме, где он
   отдаёт касания).
3. **Гейт драйвера** «display state is slept or idle»: какое именно состояние он проверяет (DRM
   connector, `fb_blank`, `lcm`-состояние) и можно ли его удовлетворить при нулевой подсветке.
4. **Переход в `GESTURE_SUSPEND_MODE`**: кто его инициирует — DRM-нотификатор
   (`MTK_DISP_EVENT_BLANK`), `fb_blank` или сам `adaptive-ts.ko` по таймеру. От ответа зависит,
   нужен ли патч модуля вообще.
5. **Жест `0xcc` (id 36)**: что происходит после успешной проверки `GestureHandle` — какое
   событие/`input_event` уходит в userspace, будит ли он систему, и можно ли получить пробуждение
   без инъекции клавиш.

## 8. Правила работы (обязательны)

Взяты из `~/.pi/agent/AGENTS.md` владельца — их надо соблюдать буквально.

1. **Симптом ≠ причина.** Сначала наблюдение (лог, дамп, `ps`, `mount`, `getprop`), потом гипотезы.
2. **3 гипотезы** с механизмом и дешёвым различающим тестом. Нет различающего теста — это догадка.
3. **Одна переменная за эксперимент**, прогноз до запуска.
4. **Нельзя писать «невозможно»** без проверки интерфейса и названного отрицательного теста
   (`cmd -l`, `cmd <svc> help`, `svc`, `dumpsys`, `settings list`). «Этот способ не сработал» ≠
   «платформа не даёт».
5. **Ребут — крайняя мера.** Один ребут на набор изменений, **спрашивать владельца**. После трёх
   ребутов в одной задаче — остановиться и доложить.
6. **Ведение журнала**: гипотеза → тест → результат → вердикт, по строке, в `DEBUG.md`. Не
   повторять уже проверенный тест.
7. **Безопасность экрана**: любой эксперимент с подсветкой обязан иметь путь восстановления.
   Выход из «тёмного» состояния: `echo 723 > /sys/class/leds/lcd-backlight/brightness` **и**
   `settings put system screen_brightness 45`. Если узел не реагирует — экран вернётся только
   после ребута (проверено), поэтому перед экспериментами фиксировать текущие значения.
8. **Не поставлять пропатченные вендорские блобы.** Правильный шаблон уже есть в модуле: при
   загрузке копируется **собственный** файл устройства, проверяются байты в известном месте и
   патч применяется через bind-mount; при несовпадении — пропуск и запись в лог
   (`post-fs-data.sh`, патч `libsl_fp_impl.so` по смещению `0x2f45c`: `2002f837` → `1f2003d5`).
9. **Горячая подмена HAL невозможна**: bind-mount держит inode (`ETXTBSY`). Обновление файлов
   модуля — через staged-файл `files/<name>.new`, который `post-fs-data.sh` подставляет при
   загрузке. Ядра/модули — только ребут.
10. **Не трогать то, что не просили**: яркость, настройки, процессы — только в рамках эксперимента,
    с восстановлением.

## 9. Что считается результатом работы

1. Отчёт с ответами на §7, каждое — с цитатой из дизассемблера/лога/дампа.
2. Один из вариантов A/B/C из §2, с точными шагами воспроизведения.
3. Замеры по §2 (расход A/B, задержка, тьма) и вывод: проходит ли критерий приёмки.
4. Если B — точные смещения, исходные и новые байты, проверка (как в `tests/patch_site.sh`) и
   процедура отката.
5. Список всего, что осталось непроверенным, с указанием, какой тест это решит.
